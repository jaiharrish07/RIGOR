## Quick start

```bash
cp .env.example .env          # then paste your Groq API key
docker compose up -d postgres # provisions rigor + rigor_test
alembic upgrade head          # creates the 5 tables
pytest -q                     # should report all tests passing
```

`docker-compose.yml` reads `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB`
from `.env`, and the app reads `DATABASE_URL` from the same file. Keep the
password identical across both — if they diverge, the app authenticates against
a container it just created and fails with `password authentication failed`.

`scripts/init_test_db.sql` creates the `rigor_test` database on first boot.
Docker only runs `/docker-entrypoint-initdb.d` when the data volume is **empty**,
so on an existing volume you must create it by hand:

```bash
docker exec rigor-postgres psql -U rigor -d postgres -c "CREATE DATABASE rigor_test;"
```

## Known deviation on the current dev machine

The Postgres container running today was **not** created by `docker-compose.yml`:

| | Running now | `docker-compose.yml` declares |
| --- | --- | --- |
| Container | `rigor-pg` | `rigor-postgres` |
| Image | `postgres:16` | `postgres:17-alpine` |
| Volume | `rigor_pgdata` | `rigor_postgres_data` |
| Created by | `docker run` (by hand) | `docker compose up` |

Both publish port **5432**, so they cannot run at the same time. Until the swap
below is performed, `docker compose up -d postgres` will fail with a port
conflict. This is the "D-series" gap referenced in `.env`.

The schema is version-agnostic — nothing in `database_schema.md` needs a
Postgres 17 feature — so this is a housekeeping change, not a functional one.

## Migrating from the hand-created container to the compose-managed one

The two containers use **different volumes**, so the old data is never touched
and the rollback below is exact.

**1. Confirm what you would be leaving behind.**

```bash
docker exec rigor-pg psql -U rigor -d rigor -c "select count(*) from papers;"
```

As of this writing that returns `0` — schema and `alembic_version` only, no
uploaded papers. If it is non-zero, do step 2. If it is zero, step 2 is optional.

**2. Take a dump anyway (cheap insurance).**

```bash
docker exec rigor-pg pg_dump -U rigor -d rigor > /tmp/rigor-backup-$(date +%F).sql
```

**3. Stop the old container. Do not delete it or its volume.**

```bash
docker stop rigor-pg
```

**4. Bring up the compose-managed one and rebuild the schema.**

```bash
docker compose up -d postgres
docker compose ps                 # wait for "healthy"
alembic upgrade head
pytest -q
```

**5. If you took a dump in step 2, restore it.**

```bash
cat /tmp/rigor-backup-*.sql | docker exec -i rigor-postgres psql -U rigor -d rigor
```

## Rollback

Nothing above is destructive, so reverting is two commands. The old container
and its `rigor_pgdata` volume are exactly as they were.

```bash
docker compose stop postgres   # frees port 5432
docker start rigor-pg          # back to the previous state
pytest -q                      # confirm
```

`.env` needs no change either way: both containers use the same user, password
and database name, so `DATABASE_URL` is valid against both.

To also discard the compose container and its volume:

```bash
docker compose down            # removes the container, keeps the volume
docker volume rm rigor_postgres_data
```

> **Careful:** `docker compose down -v` removes the volume *and* every database
> in it. Only the compose volume is affected — `rigor_pgdata` is untouched — but
> there is no undo for the compose one.

## Schema migrations (Alembic)

The URL is injected by `alembic/env.py` from `settings.database_url`;
`alembic.ini` deliberately leaves `sqlalchemy.url` blank so credentials are
never committed.

```bash
alembic current                              # which revision is applied
alembic history --verbose                    # all revisions
alembic upgrade head                         # apply everything
alembic downgrade -1                         # undo the most recent revision
alembic downgrade base                       # drop every table
alembic revision --autogenerate -m "message" # after editing app/db/models.py
```

**Always read an autogenerated migration before applying it.** Alembic does not
reliably detect renames — it emits a drop plus an add, which silently discards
the column's data.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `database "rigor_test" does not exist` | Volume predates `init_test_db.sql` | `docker exec rigor-pg psql -U rigor -d postgres -c "CREATE DATABASE rigor_test;"` |
| `password authentication failed` | `POSTGRES_PASSWORD` and `DATABASE_URL` disagree | Make them match in `.env`; the container keeps its **original** password until its volume is deleted |
| Port 5432 already allocated | Both containers running | `docker stop rigor-pg`, or stop the compose one |
| `alembic upgrade head` does nothing | Already at head | `alembic current` to confirm |
| Autogenerate produces an empty migration | `target_metadata` unset | Check `alembic/env.py` imports `Base` from `app.db.models` |
| `/health` reports `"grobid": "unavailable"` | GROBID not running | `docker compose up -d grobid` (first pull is several GB) |
